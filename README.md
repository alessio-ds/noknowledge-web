# noknowledge-web

A **browser-only** client for [noknowledge](https://github.com/alessio-ds/noknowledge):
zero-knowledge, federated, capability-mailbox messaging. Open a URL, create or
import an identity, and send end-to-end encrypted messages and files.

There is **no download, no extension, and no server-side component belonging to
the client**. All cryptography — identity keys, X3DH, the Double Ratchet,
attachment encryption, the encrypted local store — runs in the page, in
TypeScript. The only network calls are to relays, which store opaque ciphertext
and learn nothing about who is talking to whom.

```
Alice (browser)                    Relay(s)                    Bob (browser)
Ed25519 + X25519              opaque blobs only              Ed25519 + X25519
IndexedDB (encrypted)      hashed capabilities only          IndexedDB (encrypted)
      │                              │                               │
      │  1. Bob shares a signed contact card (QR / copy-paste)       │
      │◀────────────────────────────────────────────────────────────│
      │  2. fetch Bob's prekey bundle (one OPK consumed)             │
      │─────────────────────────────▶│                              │
      │  3. anonymous X3DH → Double Ratchet session                  │
      │  4. POST opaque blob to Bob's mailbox                        │
      │─────────────────────────────▶│  5. Bob fetches, decrypts, acks
      │                              │──────────────────────────────▶
```

## Features

- **Create or import an identity.** A 24-word BIP39 seed phrase is the account.
  You can also import a desktop `identity.nk` vault (including passphrase-
  encrypted ones) — the formats are byte-compatible.
- **Encrypted at rest.** Private keys, contacts, messages, ratchet state and
  prekeys live in IndexedDB, sealed with ChaCha20-Poly1305 under a key derived
  from your password with PBKDF2-SHA256 (600k iterations). The password is never
  stored.
- **1:1 text** with delivery and read receipts.
- **Encrypted attachments** (chunked, up to 25 MiB) with download.
- **Contact cards as QR or text**, plus camera scanning where the browser allows it.
- **Federation and failover.** Writes fan out to every relay in a card's relay
  set; reads use whichever answers; one relay failing is invisible.
- **Interoperable with the Python client and relay**, proven by tests (below).

## Protocol compatibility

This is a from-scratch TypeScript port of the Python `noknowledge` client, and it
is wire-compatible with it. Compatibility is enforced by tests, not by hope:

- `test/crypto.test.ts` replays deterministic vectors generated by the Python
  reference (`scripts/gen_vectors.py`) and asserts **byte-identical** results for
  canonical JSON, base64url/Crockford base32, HKDF, the ratchet KDFs,
  ChaCha20-Poly1305, BIP39 identity derivation, prekey signatures, X3DH shared
  secrets, the sealed-sender `auth` proof, and envelope padding. It also loads an
  encrypted vault produced by the desktop client.
- `test/relay.e2e.test.ts` runs two browser clients against a real Python relay:
  handshake, text, receipts, attachments, replay rejection and relay failover.
- `test/interop.e2e.test.ts` runs a TypeScript client against a **live Python
  client** through the same relay: cards, text, receipts and files in both
  directions.
- `e2e/chat.spec.ts` drives two real browsers with Playwright: create accounts,
  exchange a message, send a file, download and verify its bytes, sign out and
  unlock, and recover from the seed phrase.

## Quick start

```bash
npm install
npm run dev            # http://127.0.0.1:5173
```

The dev server proxies `/api` to a relay (`NK_RELAY`, default
`http://127.0.0.1:8000`). Run the Python relay alongside it:

```bash
# in the noknowledge checkout
uv run nk-server --host 127.0.0.1 --port 8000 --data-dir ./relay_data
```

Then open two browser profiles, create two identities, and exchange a card.

## Configuration

Relays can be edited per browser in **Settings**, and a default can be pinned at
build time:

```bash
VITE_DEFAULT_RELAYS="https://relay1.example,https://relay2.example" npm run build
```

If `VITE_DEFAULT_RELAYS` is unset, the app defaults to its own origin, which is
the right choice when the built app is served by (or reverse-proxied to) a relay.

## Building and hosting

```bash
npm run build          # -> dist/ (static files, base './')
```

`dist/` is fully static. Because the client calls relay APIs directly, a relay on
a **different origin** must allow this app's origin via CORS — see
[`docs/DEPLOY.md`](docs/DEPLOY.md). The simplest arrangement is to serve `dist/`
from the relay itself (or a reverse proxy in front of it), so everything is
same-origin and no CORS configuration is needed.

## Tests

```bash
npm run typecheck
npm test               # vitest: vectors, relay e2e, Python interop
npm run test:e2e       # Playwright: real browsers (uses system Chrome)
```

The e2e suites need the Python reference checkout and its virtualenv:

```bash
NK_PYTHON_REPO=/path/to/noknowledge \
NK_PYTHON=/path/to/noknowledge/.venv/bin/python \
npm test
```

Regenerate the cross-implementation vectors with:

```bash
NK_PYTHON_REPO=/path/to/noknowledge \
  /path/to/noknowledge/.venv/bin/python scripts/gen_vectors.py
```

## Project layout

```
src/
  crypto/    encoding (canonical JSON, base64url, base32), KDF, AEAD,
             identity + BIP39, prekeys, X3DH, Double Ratchet, padding
  wire/      relay framing, fetch transport, HTTP + multi-relay backends
  core/      contact cards, sessions, attachments, encrypted IndexedDB store,
             client orchestration, account lifecycle
  ui/        React interface
scripts/     Python vector generator and interop peer (test-only)
test/        vector, relay e2e and Python interop tests
e2e/         Playwright browser tests
```

## Security notes

- Identity and session keys never leave the browser. The relay sees random
  mailbox ids, hashed capability tokens, ciphertext and sizes.
- The password protects data **at rest**; it is separate from the identity, which
  is the seed phrase. Losing the password loses local history; losing the seed
  phrase loses the account.
- Capability tokens are bearer tokens in request headers, so an XSS on this page
  would expose them. Keep the deployment free of untrusted scripts; there is no
  third-party JS in the bundle.
- This client drops the Python client's SOCKS5/`fail_closed` proxy mode, because a
  page cannot open raw sockets. Use a browser-level proxy or Tor Browser instead.
